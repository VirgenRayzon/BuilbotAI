## Test approach and types

| Area | Approach used for this document |
| --- | --- |
| Page-level functional testing | Run the listed valid and invalid user journeys in a local headless Chrome browser, then compare the visible result and navigation with each expected result. |
| Integration checks | Where authorized, confirm Firebase-backed outcomes through the UI, including an inquiry, saved build, prebuilt catalog entry, and reservation. These are targeted workflow checks, not a comprehensive backend integration suite. |
| Authorization and validation | Exercise guest/customer/staff route guards, role-specific sections, invalid credentials or keys, malformed form input, and incompatible hardware selection. These checks do not constitute a full security audit. |
| Test design | Positive cases use valid inputs and expected permissions. Negative cases use invalid inputs, unavailable resources, or unauthorized access to confirm handled outcomes. Source review is used to define expectations; Pass/Fail comes from observed execution. |

# Manual test cases for all page routes

Source-reviewed and executed: 23 October 2026. Of 47 cases, 46 passed, 1 failed, and 0 remain unrun. The cases follow the supplied seven-column format. `Pass` means the listed steps and expected result were observed in a local headless Chrome session; `Fail` means the observed result contradicted the expectation; `Not run` means no outcome is claimed. No case is marked Pass solely because its source code exists. The owner authorized Firebase writes and asked that clearly labeled test data be left in place. New accounts, an inquiry, a saved build, a prebuilt, a synthetic inventory part, and a reservation were created in the configured Firebase project. The project-provided customer test account was used after the owner permitted sign-in's authentication-side writes. This sign-in flow can create a missing Firestore profile and attempts to update Firebase custom claims. Substitute seeded IDs and tokens for placeholders such as `{productId}` and `{token}`. Test expected behavior is based on the checked-in implementation, not on the sample screenshots' kiosk application.

The cases cover 22 primary page experiences. The repository contains 23 `src/app/**/page.tsx` files because `/group` re-exports the Team page from `src/app/group/page.tsx`; that alias was source-reviewed but not separately executed. API endpoints are exercised only through the page actions below; this is not a separate API test suite. For static pages with no form or mutable control, the negative case checks an unsupported URL parameter or non-link element rather than inventing a validation workflow.

## Execution record

On 23 October 2026, headless Chrome sessions driven by Playwright exercised the cases against the local Next.js development server at `http://127.0.0.1:9002/`. **36 cases passed, 0 currently fail, and 11 were not run.** The initial 24 pass results cover public navigation/content, catalog search, read-only detail and compatibility views, invalid-input/empty states, guest route guards, not-found handling, invalid QR feedback, and legacy redirect chains. For invalid Contact and sign-up submissions, request observation confirmed that no Contact API or Auth creation POST occurred. An invalid password-reset email was blocked by the browser's native email validation without sending a reset request.

After the owner permitted customer sign-in, the project-provided customer test account authenticated and reached `/builder` (TC-011-P). Visiting `/` under that session returned to `/builder` (TC-001-N). An invalid-format account identity with a wrong password stayed on `/signin` and displayed the handled invalid-credentials error (TC-011-N). The customer Profile displayed Settings, Reservations, Saved Favourites, Activity Logs, and Contact Inbox; selecting an existing favorite navigated to the builder (TC-018-P). All three existing favorites showed Stock Notice, and the builder omitted their unavailable parts; loading an in-stock favorite was not verified. The AI Advisor showed its budget-validation error and sent no recommendation request for malformed input (TC-017-N).

**TC-024-P retest:** A prior run showed a toast saying eight prebuilt components were ready while the builder remained at `0 / 8 PARTS`. The current working tree already contained an uncommitted change to the builder restore hook before this retest; this documentation task did not make that source change. On the fresh retest, Customize in Builder reached `/builder`, the toast reported the prebuilt load, and both the visible summary and browser-local builder state contained **8 / 8 selected components**. The latest status is Pass; the earlier failure is retained here as historical evidence. A direct page reload briefly left an account-verification overlay over the AI Advisor form, but normal in-app navigation did not reproduce it, so that observation was not recorded as a separate failed test.

The project-provided Manager and Super Admin accounts both completed System Access with tab-scoped markers (TC-014-P). A wrong Manager key showed a rejection, left no staff marker, and could not open `/admin` (TC-014-N). Signed-in customer, Manager, and Super Admin home visits routed to their appropriate workspaces (TC-001-N). Manager could select the five shared admin tabs and search matching stock cards; Super Admin-only tabs and the Stock permanent-delete control were absent (TC-019-P). Super Admin could select Sales & Analytics, Management Portal, and AI (TC-025-P). The signed-in customer and Manager legacy inquiry URLs preserved a placeholder query and opened their respective Contact Inbox views (TC-021-P and TC-022-P); no actual inquiry thread was selected or changed.

The prebuilt catalog was found to be public; the original proposed guest-denial case was corrected to its actual unmatched-search behavior before recording a result. The route's initial HTTP 200 is not treated as proof of success for a client guard or not-found page; results are based on the rendered state and final navigation. Customer and staff sign-in were authorized and may update account profiles or authentication claims.

**23 October write-enabled run:** TC-016-N showed the AM5/LGA1700 mismatch, kept the motherboard selected, and offered no Add action for the incompatible CPU. A new labeled customer account reached `/builder` (TC-012-P); a reset request for it showed Reset Link Sent, though email delivery was not verified (TC-013-P). A new labeled Manager account reached `/admin` (TC-015-P). An invalid Manager key showed a registration alert and did not grant admin access (TC-015-N); retrying the synthetic email reached the invalid-key error again, consistent with provisional account cleanup, but an independent Auth record inspection was not done. A labeled inquiry returned a success reference and appeared in the customer Contact Inbox (TC-005-P). A compatible eight-part prebuilt loaded into the customer builder, and the labeled saved configuration appeared in Saved Favourites (TC-016-P). The Manager copied an existing active product QR link; opening it as a guest resolved to that product's public detail (TC-010-P). The Manager loaded eight available parts into the staff prebuilt builder, generated a labeled new prebuilt, and found it in the public catalog (TC-020-P). A separate synthetic one-unit Monitor was added to inventory, reserved by the customer, and its order appeared in Profile Reservations (TC-023-P). These labeled test records were left in the configured Firebase project as requested; the reservation reduced that synthetic Monitor's stock from one to zero and generated related order/notification records.

A prior direct page reload had also briefly left an account-verification overlay over this form; normal in-app navigation allowed this request to proceed.
